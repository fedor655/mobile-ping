# mobile-ping

Проверка доступности серверов **с мобильного интернета реальных телефонов**.

Человек из любой точки мира заходит на сайт, вводит список адресов и получает
таблицу «устройство × цель»: что откликнулось с каждой симки, а что нет.
Физически замеры делает ноутбук дома: он по очереди подключается к Wi-Fi каждого
телефона, меряет, и возвращается в обычную сеть отдавать результаты.

```
   кто угодно                 VPS                     ноутбук дома              телефоны
   ──────────                ─────                    ────────────              ────────
   браузер  ──POST /api/jobs──►  очередь  ◄──GET poll──  агент  ──Wi-Fi──►  точка телефона 1
            ◄─GET /api/jobs/id─  заданий  ──результаты─►         ──Wi-Fi──►  точка телефона 2
                 таблица                                  возврат в обычную сеть
```

## Почему прошлая версия мерила не то

Главная проблема не в пинге, а в том, **куда уходит пакет**. На машине
одновременно живут кабель, Wi-Fi и VPN-туннели. У WireGuard маршруты
`0.0.0.0/1` и `128.0.0.0/1` перехватывают весь трафик, а Ethernet обычно имеет
метрику лучше, чем Wi-Fi. Поэтому «подключились к телефону и пингуем» на деле
означает «пингуем через кабель или через VPN».

Замеренный на этом же ноутбуке пример — три интерфейса, три разных выхода:

| привязка | внешний IP | куда на самом деле |
|---|---|---|
| Ethernet | `37.21.x.x` | домашний провайдер, напрямую |
| Wi-Fi домашней точки | `2.26.x.x` | в туннель, Германия |
| точка телефона | `195.178.x.x` | мобильный оператор |

Решение — **не трогать маршруты** (правка `ip rule` однажды уронила локальную
сеть), а привязывать каждый замер к исходному адресу Wi-Fi-адаптера:

* ICMP — `IcmpSendEcho2Ex` с параметром `SourceAddress`;
* TCP — обычный сокет с `bind((src_ip, 0))` перед `connect`.

Windows работает в strong host model, поэтому пакет с исходным адресом Wi-Fi
обязан уйти через Wi-Fi. Плюс перед каждым замером агент **проверяет внешний
IP** и помечает результат недостоверным, если выход совпал с обычной сетью.
Без этой проверки нельзя отличить «сервер недоступен» от «мы мерили не оттуда».

## Что меряется

Для каждой цели: ICMP (сколько пакетов дошло, RTT), TCP-рукопожатие по портам
и — для доменов на 443 — настоящее TLS-рукопожатие с SNI.

Одного ICMP мало: половина хостов режет ping, оставаясь живыми. Но и «порт
открыт» ничего не доказывает — российский DPI пропускает TCP-соединение и рвёт
его уже на ClientHello. Замер с мобильной сети показывает это в чистом виде:

| цель | ICMP | TCP 443 | TLS | вывод |
|---|---|---|---|---|
| `facebook.com` | 4/4, 182 мс | открыт | молчание | заблокирован |
| `max.ru` | 0/4 | открыт | TLSv1.3 | работает, режет ping |
| `ya.ru` | 4/4, 164 мс | открыт | TLSv1.3 | работает |

Цель можно задать как `1.2.3.4`, `example.com` или `1.2.3.4:8443`.

## Чему нельзя верить

Инструмент бесполезен, если тихо меряет не тот канал, поэтому каждый замер
проверяется на достоверность:

* **внешний IP обязан быть публичным и отличаться от обычной сети.** Приватный
  адрес означает, что запрос пришёл из туннеля: на машине поднят VPN с
  маршрутами `0.0.0.0/1`, и он перехватывает трафик раньше, чем сработает
  привязка к адресу Wi-Fi. Такое устройство отбраковывается — иначе
  заблокированный сайт покажется доступным;
* **исходный адрес обязан устояться.** Сразу после переподключения Wi-Fi на
  адаптере висит адрес от прошлой сессии, потом он на пару секунд исчезает.
  Замер в этом окне уходит в пустоту и выглядит как «цель не отвечает»;
* **полнотуннельный VPN на машине агента несовместим с замерами.** Агент
  предупреждает об этом при старте.

## Установка

### Сервер (VPS)

```bash
python tools/deploy.py root@ВАШ_СЕРВЕР
```

Скрипт зальёт `server/` в `/opt/mobile-ping`, создаст системного пользователя,
службу systemd, откроет порт в ufw и напечатает токен для агента. Повторный
запуск обновляет код, токен сохраняется.

Вручную то же самое:

```bash
scp -r server root@ВАШ_СЕРВЕР:/opt/mobile-ping/
ssh root@ВАШ_СЕРВЕР 'bash /opt/mobile-ping/server/deploy/install.sh'
```

Зависимостей нет — только `python3` и `sqlite3` из стандартной библиотеки.

### Агент (ноутбук, Windows)

```bash
cd agent
copy agent.config.example.json agent.config.json
```

Заполнить `agent.config.json`: адрес сервера, токен, обычную сеть и список
телефонов. Затем:

```bash
python agent.py --selftest       # диагностика, ничего не переключает
python agent.py                  # рабочий режим
```

Права администратора не нужны: `IcmpSendEcho2Ex` работает без них, профили
Wi-Fi добавляются для текущего пользователя.

## Настройки агента

```json
{
  "home":    { "ssid": "ДОМАШНЯЯ_СЕТЬ", "password": null },
  "devices": [
    { "name": "билайн №1", "operator": "билайн", "ssid": "Phone1",
      "password": "ПАРОЛЬ" },
    { "name": "мтс №1",    "operator": "мтс",    "ssid": "сеть", "open": true }
  ]
}
```

* `password: null` и без `open` — сеть уже заведена в Windows, её профиль не
  трогаем. Это важно: перезапись превратила бы домашнюю WPA2-сеть в открытую, и
  вернуться в неё стало бы нечем.
* `"open": true` — точка без пароля.
* `name` — внутреннее имя, должно быть уникальным; `operator` — что
  показывать на сайте.
* Тип защиты закрытой сети подбирается сам: сначала WPA2-PSK, затем WPA3-SAE
  (Android 13+ нередко поднимает точку в WPA3).

## Режимы запуска

```bash
python agent.py --selftest                 # адаптеры, туннели, внешний IP по каждому
python agent.py --local 1.1.1.1 8.8.8.8    # обход телефонов без сервера, таблица в консоль
python agent.py --once                     # одно задание и выход
python agent.py                            # постоянная работа
```

`--selftest` — первое, что стоит запустить на новой машине: он показывает, какие
туннели подняты и куда реально уходит трафик с каждого интерфейса.

## Устройство

```
server/app.py            HTTP API и сайт, очередь заданий в SQLite
server/static/           страница ввода и страница результатов
server/deploy/           systemd-юнит и install.sh
agent/agent.py           главный цикл: опрос сервера, обход телефонов
agent/netinfo.py         адаптеры через GetAdaptersAddresses
agent/wifi_windows.py    подключение и состояние через WLAN API + netsh
agent/probe.py           ICMP и TCP с привязкой к интерфейсу, определение egress
tools/deploy.py          заливка серверной части на VPS
```

Локализованный вывод консольных утилит нигде не разбирается: состояние Wi-Fi
читается через `WlanQueryInterface`, адаптеры — через `GetAdaptersAddresses`.
Это же решает кириллические SSID вроде «сеть»: API отдаёт сырые байты имени.

## API

Документация с примерами — на самом сервере: `http://ВАШ_СЕРВЕР:8091/api`

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/jobs` | создать проверку |
| `GET` | `/api/jobs/<id>` | состояние и результаты |
| `GET` | `/api/jobs/<id>/export.csv` | плоская таблица для анализа |
| `GET` | `/api/jobs` | последние проверки |
| `GET` | `/api/agents` | агенты и их устройства |
| `GET` | `/api/whoami` | внешний IP клиента |

CSV — длинный формат, одна строка на (устройство, цель, порт), разделитель `;`,
UTF-8 с BOM. Колонка `verdict` — готовый итог: `ok`, `blocked` (TCP открыт, TLS
сорван), `no_icmp`, `icmp_only`, `down`, `error`.

```python
import pandas as pd
df = pd.read_csv("http://ВАШ_СЕРВЕР:8091/api/jobs/<id>/export.csv", sep=";")
df[df.verdict == "blocked"][["device", "target", "tls_error"]]
```

Агентские ручки требуют `Authorization: Bearer <токен>`:
`GET /api/agent/poll`, `POST /api/agent/hello`,
`POST /api/agent/jobs/<id>/device`, `POST /api/agent/jobs/<id>/complete`.

Пример:

```bash
curl -X POST http://ВАШ_СЕРВЕР:8091/api/jobs \
  -H 'Content-Type: application/json' \
  -d '{"targets": "1.1.1.1\n8.8.8.8", "ports": "443,80"}'
```

## Эксплуатация

```bash
systemctl status mobile-ping
journalctl -u mobile-ping -n 50
```

База: `/var/lib/mobile-ping/mobile-ping.db`, токен: `/etc/mobile-ping.env`.

Задание, взятое агентом и не обновлявшееся 30 минут, помечается провалившимся —
агент мог уйти в перезагрузку прямо на точке телефона.

## Ограничения

* Агент только под Windows: используются WLAN API и `IcmpSendEcho2Ex`.
  Логика переносима, но под Linux нужен вариант на `nmcli` и `SO_BINDTODEVICE`.
* Только IPv4.
* Телефоны обходятся последовательно — иначе пришлось бы держать по Wi-Fi
  адаптеру на каждый.
* Сайт отдаётся по HTTP. Создание заданий не требует авторизации, так что порт
  разумно не публиковать в открытый интернет без нужды.
